独自Webデザイン定義書

1. 目的と適用範囲

本定義書は、コーポレートサイト、サービスサイト、SaaS、管理画面、業務アプリ、LPなどのWeb UIを、 ブランド・ユーザビリティ・アクセシビリティ・実装品質の観点から一貫して設計するための共通標準である。

この定義書の最重要ルール ルールそのものを守ることより、ユーザーの目的達成を優先する。ただし、アクセシビリティ、安全性、 法令・規約、データ保護に関わる要件は「好み」で例外化しない。

規範レベル

MUST 必須。原則として例外不可。 SHOULD 推奨。合理的な理由があれば例外可。 MAY 任意。文脈に応じて採用する。

対象者

Designer

原則・トークン・パターン・コンポーネントを使い、独自UIの乱立を防ぐ。

Engineer

セマンティックHTML、Design Tokens、状態管理、アクセシビリティを実装契約として扱う。

PM / PO

見た目ではなく、ユーザー課題・情報優先度・エラー回復性を仕様として判断する。

Writer / Marketer

UIテキスト、見出し、CTA、エラー、ヘルプを同じVoice & Toneで設計する。

2. デザイン原則

01. Task First

ユーザーの目的達成を最短にする。装飾、社内都合、技術都合をユーザーのタスクより上に置かない。

02. Clarity over Cleverness

賢そうなUIより、初見で意味が分かるUIを選ぶ。慣習的な表現を意図なく崩さない。

03. Accessible by Default

アクセシビリティは後工程の検査ではなく、設計・コンポーネント・実装の初期条件にする。

04. Consistent, not Uniform

同じ意味には同じ表現を使う。一方、異なる文脈を無理に一つのコンポーネントへ押し込めない。

05. Content is Interface

ラベル、説明、エラー、見出し、空状態までUIの一部として設計する。言葉を最後に埋めない。

06. Responsive by Meaning

画面幅だけで縮小しない。情報の優先度、入力方法、タスク量に応じて再配置・省略・段階表示する。

07. Evidence Evolves the System

定義書は完成品ではない。ユーザー調査、障害、問い合わせ、分析、実装知見に基づき更新する。

08. One Source of Truth

色・余白・文字・状態・コンポーネント仕様をDesign Tokensと実装コードで同期し、二重管理を減らす。

3. 判断優先順位

設計上のルールが衝突した場合、次の順序で判断する。

  1. 安全・法令・プライバシー・アクセシビリティ
    利用不能や誤操作、権利侵害を防ぐ。
  2. ユーザーの目的達成と情報理解
    完了率、理解、回復性、負荷を優先する。
  3. 一貫性と予測可能性
    既存の慣習・システム・用語との整合を取る。
  4. 運用性・保守性・性能
    継続して品質を維持できる構造を選ぶ。
  5. ブランド表現
    意味・操作性を壊さない範囲で個性を出す。
  6. 新規性・装飾性
    上記を満たした後に採用する。

4. Foundations

見た目の数値ではなく「意味」を先に定義し、Primitive Token → Semantic Token → Component Tokenの3層で管理する。

4.1 Color

Token用途ルール
color.text.primary本文・主要ラベル背景とのコントラストを最優先。
color.text.secondary補助説明重要情報には使わない。
color.action.primary主操作同一画面で乱用しない。
color.status.success成功色だけで意味を伝えない。
color.status.warning注意確認が必要な状態。
color.status.dangerエラー・破壊操作通常操作の強調色として使わない。
  • MUST 色名ではなく役割名でSemantic Tokenを付ける。
  • MUST 状態を色だけで区別しない。ラベル、アイコン、形状を併用する。
  • SHOULD Light / Dark / High Contrastなどテーマ差をTokenで吸収する。

4.2 Typography

Role目安用途
Display40–64px / 1.15限定的なヒーロー表現
Heading 132–40px / 1.25ページ主題
Heading 224–32px / 1.3主要セクション
Heading 320–24px / 1.4下位セクション
Body16px / 1.6–1.8標準本文
Small13–14px / 1.5補助情報のみ
  • 本文の標準サイズは16px相当を基準にする。
  • 見出し階層は視覚サイズではなく文書構造に従う。
  • 日本語の長文は行長35〜45文字程度を目安にし、極端な横長を避ける。
  • 数字を比較するUIではtabular numeralsを検討する。

4.3 Spacing

基本単位は4px。主要スケールは 4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 96。同じ階層には同じ余白を使い、意味の近さを余白で表現する。

4.4 Radius / Border / Elevation

  • Radiusは 4 / 8 / 12 / 16 / full 程度に限定し、用途で使い分ける。
  • 境界表現は「余白 → 背景差 → Border → Shadow」の順に、必要最小限を選ぶ。
  • Elevationは階層を意味するときだけ使う。Shadowを装飾として乱用しない。

4.5 Iconography

  • アイコンのみの操作にはアクセシブルネームと必要に応じてTooltipを付ける。
  • アイコンの線幅・ViewBox・光学サイズを揃える（Apple SF SymbolsのWeight/Scale整合、IBM Carbonの16/20/24/32pxグリッドのような「サイズごとに再設計する」思想を採用）。
  • 独自アイコンを作る前に既存セットで意味が表せないか確認する。

4.6 Motion

  • Motionの目的は「状態変化・位置関係・因果関係」を説明すること。
  • 標準Durationは100〜250ms、複雑な遷移でも400ms以内を基本とする。
  • Easingは「開始は速く終わりは滑らかに」を基本形とし、画面外から入る要素はEmphasized（減速強め）、画面内で完結する変化はStandard（対称的）を使い分ける（Material 3 Motion / Fluent 2 Motionの分類に準拠）。
  • prefers-reduced-motion を尊重し、不要な移動・点滅・自動再生を抑制する。低モーション環境ではDurationを短縮するか、Fade中心の代替遷移に切り替える。

4.7 Dark Mode / テーマ

  • Light / Darkは反転処理ではなく、Semantic Tokenの値を差し替えるだけで成立する設計にする。
  • Dark面では影（Shadow）による階層表現が弱まるため、Surfaceの明度差・境界線・Elevation用のOverlay（白の半透明レイヤーを重ねるMaterial的な手法）で階層を補う。
  • 純黒・純白は避け、コントラスト過多によるハレーションを抑えたSurface色を使う。
  • ブランドカラーはDark面でそのまま使うと彩度過多になりやすいため、明度・彩度を調整したDark用Aliasを用意する。

5. レイアウト

5.1 情報階層

ページは「Global → Page → Section → Component → Element」の階層で設計する。見た目のグルーピングとDOMの意味構造を可能な限り一致させる。

5.2 Grid

  • Desktopは12-columnを標準候補とするが、コンテンツ用途に応じて固定しない。データ密度が高い業務UIでは、IBM Carbonの「2x Grid」（16px単位のガター、Wideでは16列まで拡張可能なグリッド）のように、より細かい列数を許容する。
  • 本文コンテンツには最大幅を設ける。画面が広いほど行を長くする設計は避ける。
  • 左右余白はViewportに応じて可変にする。
  • カードの列数ではなく「カードが読める最小幅」を基準に折り返す。

5.3 Page Types

Content Page

記事、ヘルプ、ガイド。読解性・見出し構造・目次を優先。

List / Search

検索、絞り込み、並び替え、結果件数、空状態を一体設計。

Detail / Object Page

対象の識別情報、主要アクション、属性、関連情報の順に配置（SAP Fioriの Object Page Floorplanのようにヘッダー固定＋セクションアンカーで長い詳細情報を辿らせる構成も検討）。

Dashboard / Overview

KPIを「重要度順」に配置し、色ではなくラベルと比較軸を明示。

Form / Wizard

入力目的、進捗、保存、エラー回復を中心に設計。複雑な手続きはGOV.UKのように「1画面1質問」に分割することを検討する。

Marketing / LP

価値提案、根拠、詳細、CTAの順で情報を積み上げる。

5.4 密度モード（Density）

業務系・データ集約型UIでは、マウス操作中心の高密度表示（Compact）とタッチ操作中心の余裕ある表示（Comfortable / Cozy）を切り替えられるようにする （Salesforce Lightningの Compact / Comfortable、SAP Fioriの Cozy / Compact modeを参照）。切り替えても操作対象の最小タップ領域とコントラストは損なわない。

6. レスポンシブ / Adaptive

Breakpointはデバイス名ではなく「レイアウトが破綻する点」で決める。 Mobile / Tablet / Desktopという分類はテスト管理には使えるが、CSS設計の唯一の根拠にはしない。
  • MUST 横スクロールを主要な閲覧方法にしない。例外は表・タイムライン等、意味的に横方向が必要なUI。
  • MUST 文字拡大や狭幅でも主要機能と情報を失わない。
  • SHOULD Desktopの情報を単に非表示にせず、優先度に応じて折りたたみ・別導線・詳細化を使う。
  • SHOULD Hover前提の情報や操作を作らない。
  • SHOULD Touchでは操作領域を十分に確保し、隣接操作の誤タップを避ける。

7. コンポーネント

コンポーネントは「見た目の部品」ではなく、意味・状態・振る舞い・アクセシビリティを含む契約である。

7.1 必須状態

Interactive componentは該当する範囲で default / hover / focus-visible / active / selected / disabled / loading / error / success を定義する。

7.2 各コンポーネントで必ず定義する項目

  • Purpose — 何を解決するか
  • When to use / When not to use
  • Anatomy — 構成要素
  • Variants / Sizes / States
  • Behavior — マウス、タッチ、キーボード
  • Content — ラベル、長さ、文体
  • Accessibility — Name / Role / Value / Focus / Keyboard
  • Responsive behavior
  • Design Tokens
  • Code API / Props
  • Test cases

7.3 標準コンポーネントセット

Button、Link、Icon Button、Input、Textarea、Select、Checkbox、Radio、Switch、Search、Tabs、Accordion、Disclosure、Dialog、Drawer、Tooltip、Popover、Toast、Alert、Breadcrumb、Pagination、Table、Card、Badge、Tag、Avatar、Progress、Skeleton、Empty State、File Upload、Date/Time、Navigationを基本セットとする。

新規コンポーネントを追加する条件 既存コンポーネントのVariantで表現できず、複数画面で再利用され、独自の意味・振る舞い・アクセシビリティ要件を持つ場合に限る。

7.4 プラットフォーム規約への準拠

Web上に構築する場合でも、OSやアプリの慣習を無視しない（Apple Human Interface GuidelinesのPlatform Conventions、 Microsoft Fluent 2のクロスプラットフォーム思想を参照）。

  • ショートカットキー、戻る操作、共有・コピーの挙動は、実行環境（デスクトップOS / モバイルOS / ブラウザ）の標準に合わせる。
  • PWAやハイブリッドアプリでは、Webの慣習とネイティブの慣習が衝突する箇所（戻るジェスチャー、Pull-to-refresh、Safe Area）を明示的に決める。
  • 入力方法（マウス、タッチ、ペン、キーボード、音声）ごとにヒットエリアとフィードバック速度を最適化する。

8. UXパターン

コンポーネント単体ではなく、ユーザーのタスク単位で標準パターンを定義する。

Loading

処理の存在を即時に知らせる。長時間処理は進捗・キャンセル・バックグラウンド化を検討する。

Empty State

「何もない」だけで終わらせず、理由と次にできることを示す。

Error Recovery

何が起きたか、何が保持されたか、次に何をすればよいかを示す。

Destructive Action

削除等は影響範囲を明示。取り消し可能ならUndoを確認Dialogより優先検討する。

Search & Filter

現在条件、結果件数、条件解除を明確にする。0件時に回復手段を提示する。

Permission

権限不足を「利用不可」で終わらせず、必要権限と取得方法を説明する。

9. フォーム

  • MUST 全入力欄に視覚ラベルを用意する。Placeholderをラベル代わりにしない。
  • MUST 必須・任意の表現ルールを一貫させる。
  • MUST エラーは該当項目の近くに表示し、入力内容を原則保持する。
  • MUST エラーの存在だけでなく、修正方法を伝える。
  • SHOULD ユーザーが知っている順・自然な順に質問する。
  • SHOULD 同じ情報を再入力させない。
  • SHOULD 入力形式は可能な範囲でシステム側が吸収する。
  • SHOULD 長いフォームは意味のある単位で分割し、進捗と保存状態を示す。複雑な申請はGOV.UK Design Systemのように「1画面1質問」に分割し、質問間の依存関係を分岐で処理する。
  • SHOULD Autocomplete属性（氏名・住所・電話番号・メール等）を適切に指定し、ブラウザの自動入力を活かす。

エラーメッセージの型

対象 + 問題 + 解決方法 の順で書く。「入力エラーです」のような抽象表現だけで終わらせない。

エラーサマリー（Error Summary）

項目数が多いフォームでは、送信時に画面上部へエラー一覧を表示し、各項目へのアンカーリンクを設ける （GOV.UK Design Systemの Error Summary パターン）。フォーカスはエラーサマリーの見出しへ移動し、 スクリーンリーダー利用者にも件数と内容が即座に伝わるようにする。

ヒントテキストと必須表現

入力形式やフォーマット例（例：郵便番号は「123-4567」の形式）はラベル直下のヒントテキストとして常時表示し、 Placeholderに埋め込んで消えてしまう情報にしない（GOV.UK / e-Govの入力支援パターン）。

10. UXライティング / Voice & Tone

10.1 Voice

基本人格は「明確・誠実・簡潔・落ち着き」。ユーザーを責めない。システム内部用語をそのまま出さない。

10.2 UI Text

  • Buttonは可能な限り動詞で始め、結果を予測できるラベルにする。
  • 見出しは内容を要約し、「お知らせ」「情報」のような抽象語だけにしない。
  • 確認Dialogは「本当に〜しますか？」より、対象・結果・不可逆性を具体的に書く。
  • 同一概念には同一用語を使用する。類義語を装飾目的で使い分けない。
  • 専門用語は対象ユーザーが日常的に使う場合のみ採用し、必要なら説明する。
  • エラーや空状態は次のアクションまで書く。

10.3 Content Design

情報量を増やす前に、ユーザーが「この瞬間に必要な情報」を特定する。重要情報はProgressive Disclosureで隠しすぎない。

10.4 Plain Language（平易な言葉）

GOV.UKやNHS Design Systemの content style を参考に、一文を短くし、専門用語・受動態・二重否定を避ける。 ユーザーが検索で使う言葉（サービス提供者の内部用語ではなく利用者の語彙）を見出しやラベルに使う。 一つの段落は一つの考えに絞り、箇条書きや番号付き手順を積極的に使う。

11. アクセシビリティ

標準品質: WCAG 2.2 Level AAを基準とする。 チェックリストを最後に回すのではなく、Design Token、Component、Pattern、Code Review、QAへ組み込む。

11.1 Perceivable

  • 意味のある画像には適切な代替テキストを付け、装飾画像は支援技術から除外する。
  • 色だけで状態・必須・成功・エラーを伝えない。
  • テキストと重要UIのコントラストを検証する。
  • 字幕・トランスクリプトなど、メディアの代替手段を用意する。

11.2 Operable

  • 全機能をキーボードだけで操作可能にする。
  • Focus indicatorを消さない。現在位置が視覚的に分かるようにする。
  • Drag、Swipe、Hoverのみに依存しない代替操作を用意する。
  • Focus trapはModal等、必要な文脈だけで使う。

11.3 Understandable

  • ナビゲーション・ボタン・入力の意味を一貫させる。
  • 入力で突然大きな画面変化を起こさない。
  • エラー位置と修正方法を具体的に伝える。

11.4 Robust

  • まずSemantic HTMLを使い、ARIAは不足する意味を補うために使う。
  • Name / Role / Value / Stateが支援技術へ正しく伝わることをテストする。
  • DOM順序と視覚順序を不必要に逆転させない。

12. キーボード操作パターン

WAI-ARIA Authoring Practices Guide (APG) が定義する、代表的なCustom Widgetのキーボード操作を実装契約として採用する。 独自のキー割り当てを作らず、ユーザーの既存学習を再利用する。

Widget主要キー操作
Tabs矢印キーでタブ間移動、Home/Endで先頭・末尾へ。Tabキーはタブリストの外へフォーカスを移す。
Menu / Menu ButtonEnter・Space・下矢印でメニューを開く。矢印キーで項目移動、Escで閉じてトリガーへフォーカスを戻す。
Combobox下矢印でリストを開く。矢印キーで候補移動、Enterで確定、Escで閉じて入力値を保持。
Dialog（Modal）開いた瞬間にフォーカスをダイアログ内へ移動しTrapする。Escで閉じ、閉じた後は呼び出し元要素へフォーカスを戻す。
Disclosure / AccordionEnter・Spaceで開閉。Tabで次の操作可能要素へ、開閉状態はaria-expandedで伝える。
Listbox矢印キーで選択移動、Home/Endで先頭・末尾、複数選択時はShift+矢印で範囲選択。
Slider矢印キーで値を増減、Home/Endで最小・最大値、Page Up/Downで大きな刻み。
TooltipフォーカスやHoverで表示、Escで消去。フォーカスが外れれば自動的に消える。
  • MUST Focus-visibleなインジケーターを、キーボード操作時に必ず視認できる状態にする。
  • MUST 独自Widgetを作る際は、対応するAPGパターンが存在するか先に確認する。
  • SHOULD Escキーは「直前の状態に戻る」という一貫した意味で使い、確定操作には割り当てない。

13. インタラクション

12.1 Feedback

ユーザー操作には遅延なくフィードバックを返す。保存・送信・削除・コピー等は成功したかどうかを明示する。

12.2 Focus

画面遷移、Dialog、動的追加、エラー発生後に「次に操作すべき位置」へ自然にフォーカスを移す。ただしユーザーの文脈を奪う自動移動は避ける。

12.3 Disabled vs Read-only

Disabledは理由が分からなくなりやすい。利用条件を説明できるなら、操作可能状態のまま理由を返す、または補助説明を添える。閲覧のみ可能ならRead-onlyを使う。

12.4 Optimistic UI

失敗時に安全にロールバックできる操作では、即時反映を検討する。金銭・権限・不可逆操作ではサーバー確定前の成功表示を避ける。

14. データ表現 / Visualization

  • 比較が主目的ならCardの羅列よりTableを検討する。
  • Chartは「グラフを置く」ことが目的ではなく、比較・傾向・構成・分布など質問に答えるために使う。
  • 凡例だけに依存せず、可能ならデータへ直接ラベルする。
  • 色覚差を考慮し、色以外の識別要素（パターン、形状、直接ラベル）を持つ（IBM Carbon Data Visualizationの配色ガイドラインを参照）。
  • 0起点が意味を持つ棒グラフなど、視覚的誤解を生む軸操作を避ける。
  • 数値の単位、期間、母数、更新時刻を必要に応じて明記する。
  • カテゴリ配色は14系統程度までに抑え、系列を追加するほど識別困難になることを前提に「上位N件＋その他」の集約を検討する。
  • 業務用の高密度Table（Ant Design、SAP Fioriの List Report等）では、列の固定・ソート・列表示切替・行内アクションを標準機能として設計する。

15. 国際化・多言語・RTL

単一言語・単一文化圏を前提に設計しない。文言追加ではなく、レイアウト・入力・日付表現まで含めて多言語を初期設計に含める。

  • MUST 固定幅Boxへテキストを詰め込まない。言語によって文字数は30〜200%変動し得る前提でレイアウトする。
  • MUST RTL（アラビア語・ヘブライ語等）対応が必要な場合、margin-leftのような物理方向のCSSではなく、margin-inline-start等の論理プロパティを使用する。
  • SHOULD 日付・時刻・数値・通貨・氏名の順序（姓名 / 名姓）はロケールに応じてフォーマットを切り替える。
  • SHOULD アイコンの意味が文化・言語によって変わらないか確認する（矢印の進行方向、色の意味等）。
  • SHOULD 翻訳時に文脈が失われないよう、UI文言には用途・出現画面のメモを添える。
  • MAY 和暦・郵便番号・全角/半角のゆらぎなど、日本語UI特有の入力ゆらぎはシステム側で正規化する（デジタル庁DADS / e-Govの知見）。

16. 実装標準

16.1 Design Tokens

:root {
  --color-text-primary: ...;
  --color-surface-default: ...;
  --color-action-primary: ...;
  --space-1: 0.25rem;
  --space-2: 0.5rem;
  --radius-control: ...;
  --motion-duration-fast: ...;
}

Adobe Spectrum 2 / Salesforce Lightning Design Systemの命名思想を参考に、Tokenは Global（生の値）→ Alias / Semantic（役割）→ Component（部品固有）の3層で命名し、 画面やコンポーネントはComponent Tokenのみを参照する。

  • Figma上の変数とコードのToken名・意味を可能な限り一致させる。
  • コンポーネント内にブランド色やpx値を直接散在させない。
  • Primitive Tokenを画面実装から直接参照しすぎず、Semantic Tokenを介する。

16.2 HTML / CSS / JS

  • Native HTMLで表現できる要素はNativeを優先する。
  • 見た目の都合でbuttonとlinkの意味を入れ替えない。
  • JavaScriptなしでも最低限のコンテンツ意味構造が保たれることを目指す。
  • LayoutはFlexbox / Gridを基本とし、絶対位置依存を最小化する。
  • 状態はCSS classだけでなくDOM属性・ARIA stateと整合させる。
  • RTL対応が要件にある場合は、left/rightではなく論理プロパティ（inset-inline-start等）を用いる。

16.3 Component API

  • Propsは視覚的実装名ではなく意味で設計する。
  • variant="danger" のようなSemantic APIを優先し、red=true のような表現を避ける。
  • アクセシビリティに必要な属性を利用者へ丸投げしない。

16.4 Performance

  • 画像は用途に適した形式・サイズで配信し、レイアウトシフトを防ぐ。
  • Web Fontは必要なウェイトに限定し、Fallbackを定義する。
  • 重要UIを巨大なJSの読み込み完了まで操作不能にしない。

17. 品質保証

品質は「デザインレビューだけ」で担保しない。複数レイヤーで検証する。

Layer検証

18. 運用・ガバナンス

18.1 Component Lifecycle

Proposal → Experimental → Stable → Deprecated → Removed の状態を持つ。Breaking Changeには移行方法と期限を付ける。

18.2 変更提案に必要な情報

  • 解決したいユーザー課題
  • 既存ルールで解決できない理由
  • 利用画面・ユースケース
  • Accessibilityへの影響
  • Responsive / Themeへの影響
  • 実装APIとTokenへの影響
  • 移行コスト
  • 検証結果・ユーザー調査

18.3 Versioning

  • PATCH: 表記修正、互換性のある微修正
  • MINOR: 新Component、Variant、Pattern
  • MAJOR: Token削除、API変更、見た目や動作の大規模変更

18.4 例外管理

例外は「その場限りのCSS」ではなく記録する。理由、影響範囲、期限、標準へ戻す条件を残す。

19. Definition of Done

以下を満たして初めて「デザイン完了」とする。

  • ページのユーザー目的が一文で説明できる
  • 主要アクションと情報優先度が明確
  • 既存Component / Patternを優先している
  • Loading / Empty / Error / Success / Disabled等の状態が定義済み
  • Mobile〜Wide screenまで破綻しない
  • 200% Zoom、Keyboard、Focus orderを考慮済み
  • 見出し構造・ランドマーク・ラベルが設計済み
  • Color contrastと色以外の識別方法を確認済み
  • UIテキスト・エラーメッセージ・空状態が完成している
  • 実装TokenとFigmaの意味が一致している
  • 破壊的操作・権限・個人情報の扱いを確認済み
  • 分析イベント・ログ・成功指標が必要なら定義済み
  • 自動アクセシビリティテストだけでなく手動操作も確認済み
  • Custom WidgetはWAI-ARIA APGの該当パターンとキーボード操作が一致している
  • 多言語化・RTL・文字数変動を想定したレイアウト崩れがない
  • 変更理由・仕様・利用方法がドキュメント化されている

20. コンポーネント仕様書テンプレート

新規Componentは以下の章立てを標準とする。デザインとコードの仕様書を分けず、同じ情報構造を共有する。

  1. Overview — 役割を1〜3文で説明
  2. When to use — 適切なユースケース
  3. When not to use — 代替Componentを提示
  4. Anatomy — 必須・任意パーツ
  5. Variants — 意味の違いを説明
  6. States — Default / Hover / Focus / Active / Disabled / Loading / Error...
  7. Layout & Spacing — サイズ、配置、余白
  8. Responsive — 狭幅・Touch・Text resize
  9. Content — Label、文体、文字数、禁止表現
  10. Behavior — Pointer / Keyboard / Focus / Dynamic update
  11. Accessibility — Semantics、ARIA、Screen reader、Contrast
  12. Tokens — 利用するSemantic / Component Token
  13. Code API — Props、Events、Slots
  14. Examples — Do / Don'tではなく理由が分かる使用例
  15. Tests — Unit / Interaction / Visual / Accessibility
  16. Changelog — Breaking changeとMigration
